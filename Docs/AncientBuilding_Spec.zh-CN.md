## 2. 屋顶分类（图1）—— 以及为何它是两套生成器，而非九套

| 图1标签 | 中文 | 族群 |
|---|---|---|
| Pyramidal | 攒尖顶 | 集中式 |
| Round | 圆攒尖 | 集中式 |
| Helmet | 盔顶 | 集中式 |
| Hollow | 盝顶 | 集中式 |
| Flush Gable | 硬山 | 脊式 |
| Overhanging gable | 悬山 | 脊式 |
| Hip | 庑殿 | 脊式 |
| Gable and hip | 歇山 | 脊式 |
| Round Ridge | 卷棚 | 脊式 |

公式8使这种划分成为结构性的，而非仅是外观上的：

```
sides == 4  ⟺  ratio != 1
sides != 4  ⟺  ratio == 1        where ratio = Building.width / Building.depth
```

因此矩形平面永远是四边形（→ 脊式屋顶），而多边形平面被强制为正方形/规则形（→ 集中式屋顶）。
**两套屋顶生成器覆盖全部九种类型**；同一族群内部的差异仅在于脊线曲线形状和檐口处理方式。

## 4. 层级树（图11）—— 映射到 PCG 图

五个层级，根节点在第4层：

```
Layer 4  建筑（Building）
Layer 3  屋顶（Roof）              主体（Body）              基座（Base）
Layer 2  屋顶望板                  斗拱   房间               栅栏
Layer 1  屋面瓦                   斗拱构件  房间构件           栅栏构件      台阶
Layer 0  筒瓦/板瓦/滴水            座斗 拱  柱 门              望柱          台阶主体
         椽子、脊                            墙                栏板          垂带
                                                                            台基
```

两种连接边：
- **绿色** = 子节点是通过沿父节点 spline 进行*构件实例化*产生的（`id_high = id_low + 1`）
- **灰色** = 子节点是通过若干节点的*直接组装*产生的（`id_high = max(child ids) + 1`）

编辑一个节点会使从它到根节点的整条路径都变脏（需要重新计算）。

**这是一个按层级索引进行脏标记传播的 DAG —— 也就是 PCGODOT 的求值器本来就是的东西。**
我们不需要重新构建它；我们需要把这套建筑图式*表达*为一个图。

## 5. 表面操作 A —— Spline 网格生成（公式1-5）

### 5.1 顶点位置（公式1）—— 是斜接（miter join），而不是扫描轮廓

给定带有切向量/法向量/副法向量 `T_i, N_i, B_i`（i ∈ [1,n]）的 spline 节点 `p_i`，
以及一个放置在 `(T_1, p_1)` 平面上的、有 `m` 个节点的用户轮廓：

```
d          = (p_{i+1} - p_i) / ||p_{i+1} - p_i||
c_j^{i+1}  = c_j^i + [ (-T_{i+1} · (p_{i+1} - c_j^i)) / (-T_{i+1} · d) ] · d
```

双重负号相互抵消，因此从实现角度看这就是一次**射线/平面求交**：

```
t = dot(T_{i+1}, p_{i+1} - c_j^i) / dot(T_{i+1}, d)
c_j^{i+1} = c_j^i + t * d
```

请仔细阅读，因为这是该论文真正的贡献点，而且很容易被误实现：**轮廓从未被重新定向。**
每个轮廓顶点沿着*线段*方向 `d` 直线运动，并被垂直于*下一个节点切向量*的平面所截停。
这就是一个斜接（miter joint），与偏移一条折线时使用的构造方式相同。

在动手实现之前值得了解的一些后果：
- 相邻线段精确共享它们的边界环，因此侧面保持平面且相连 —— 这正是尖锐拐角不再收缩变尖的原因
  （对比图5a/5b 与图5c）。
- 横截面面积在弯折处**不会**保持不变：拐角外侧会变宽。这对于瓦垄脊来说是正确的，
  而这正是旧的扫描方法出错的地方。
- **退化情况**：当转角接近180°时 `dot(T_{i+1}, d) → 0`，`t` 会发散。需要一个防护措施
  （对 `t` 进行截断，或者拆分该节点）。论文中并未提及这一点。

### 5.2 位移曲线（公式2）

```
c_disp[i][j] = c_j^i + φ · y(i/n) · normalize(c_j^i - p_i)
```

一条由 `φ` 缩放的用户曲线 `y: [0,1] → R`，使每个轮廓顶点**径向**远离其脊线点位移。
注意这里的参数是 `i/n`，即按*节点编号*索引，而非按弧长索引。Godot 原生的 `Curve` 资源
可以直接替代 `y`。

### 5.3 方向约束（公式3-5）

```
c_constrain[i][j] = c_j^i + φ · y(i/n) · W · D

D = normalize(c_j^i - p_i)   if δ >  π/2
  = B_i                      otherwise

W = 1   if α ≤ δ
  = 0   otherwise            where α = angle(B_i, c_j^i - p_i)
```

语义：当 `δ ≤ π/2` 时，只有朝"上"的轮廓顶点（在副法向量 `δ` 范围之内的那些）会被选中，
且它们沿固定的副法向量而非径向移动。这正是实现单侧轮廓的机制 —— 台阶、脊尾（图6）。

## 6. 表面操作 B —— 构件实例化（公式6-7）

对于每个 spline 线段，设 `d` = 源构件沿其自身轴向的宽度：

```
k       = ceil( ||segment|| / d )                      (公式6)
s_l^i   = p_i + (l-1) · d · normalize(p_{i+1} - p_i)   (公式7)，  l ∈ [1,k]
```

实例保留源缩放；朝向由 `p_i → p_{i+1}` 决定。

- **裁剪多余部分**（§3.2.2）：最后一个实例会伸出边界；用位于 `p_{i+1}` 处、
  法向为 `p_i → p_{i+1}` 的平面对其进行裁剪。
- **径向裁剪**（§3.2.3，图9）：两个参数 —— `ω` = 裁剪区域宽度，`λ` = 二分迭代次数，
  给出 `2^λ` 个裁剪方向（`λ=0 → {0}`，`λ=1 → {0, π}`，`λ=2 → {0, π/2, π, 3π/2}`）。
  一个包围盒完全位于裁剪区域内的实例会被丢弃；部分位于其中的实例会被裁剪。
  这就是门洞和台阶开口从栅栏或墙环中被冲切出来的方式。

## 7. 屋顶构造（图14、图15）

图14c 给出了改进后的屋顶框架，它是一组命名过的控制点：

- `p^BD` 建筑基准点，`p^MRg` 正脊，`p^Rg` 脊，`p^RgT` 脊尾，`p^Ev` 檐口，`p^EvC` 檐角
- 弯曲手柄 `b^RfS`（屋面）、`b^Rg`、`b^RgT`、`b^Ev`

脊线形状是一条**三次贝塞尔曲线**，正是这一点使得该框架能够表达此前方法无法表达的
盔顶和卷棚屋顶。

瓦片机制（图15）是需要照搬的部分：

1. 屋面由**脊曲线**（图15中的红色）界定边界。
2. 对该表面进行分段，并生成横跨其上的**子曲线**（蓝色）—— 这些即为椽子/瓦垄的线。
   它们的节点即图中的青色点。
3. 沿每条子曲线实例化瓦片构件（操作B）。
4. 通过在脊曲线和子曲线上运行操作A，生成脊和椽子。
5. `Cr ∈ [0,1]` 独立于脊线形状控制瓦片覆盖范围：`Cr=1` 覆盖整个屋面，`Cr=0.4` 仅覆盖
   上部40%，其余部分裸露（图15a 与图15b）。

因此屋顶是**在脊曲线之间放样出的表面、再重采样为若干子曲线**，而不是一根扫描出的管状体。
操作A和操作B随后都应用于这个表面之上。

### 屋顶坡度（公式9-10）

尽管是为框架提取而给出的，但对内置框架而言也是一个可用的默认值：

```
Roof.height = 1.3 × Building.depth / ((n_R - 1) / 2)
```

`n_R` 由屋顶类型设定，最小值为5。这实质上就是"举架" —— `n_R` 即椽子的道数（步架）。
它将屋顶高度与平面进深绑定，而非直接暴露一个原始数值。

## 8. 框架推导（表1）

一个模数驱动一切：

```
D = Building.width × 0.8 × (1/11)
```

| 部件 | 组件 | 属性 | 默认值 |
|---|---|---|---|
| 屋顶（Roof） | | 位置 | `(0, 11D + bracket.height, 0)` |
| 主体（Body） | 斗拱（Brackets） | 位置 | `(0, 11D, 0)` |
| | 墙（Wall） | 位置 | `(0, Base.Platform.height, 0)` |
| 基座（Base） | 栅栏（Fence） | 位置 | `(0, Base.Platform.height, 0)` |
| | | ω | `fence.width × 2` |
| | | λ | `1` |
| | 台基（Platform） | 位置 | `(0, 0, 0)` |
| | | 高度 | `2D` |
| | 台阶（Steps） | 位置 | `(0, 0, 0)` |
| | | 宽度 | `Fence.ω` |
| | | 进深 | `Steps.width × 1.1` |
| | | 数量 | `2^Fence.λ` |
| | | 方向 | 由 `Fence.λ` 决定 |

`fence.width` 和 `bracket.height` 来自用户提供的具体组件。

由于 `11D = Building.width × 0.8`，整张表可以归纳为一条易读的规则：

> **檐口高度 = 0.8 × 建筑宽度。** 台基占其中的2/11，墙体占余下的9/11，屋顶坐落于
> 斗拱之上。

这是对《营造法式》中"材份/斗口"模数体系的一种简化。对游戏而言已经够用；在代码中
应说明这一点，以免有人误以为它是权威依据。

### 阶段1 —— Spline 网格生成（§3.1，公式1-5）—— **已完成，已验证**

  y(x) 的 `Curve`；φ、δ；以及在论文的斜接方式与既有方案之间切换的 `mode` 开关。
- `Game/Develop/SweepValidate.tscn` —— 验证工具场景。渲染结果输出到
  `Game/Develop/SweepShots/`（已加入 gitignore），并打印方向约束的数值 PASS/FAIL 结果。

在实现过程中做出的、论文未覆盖的决策：

1. **内部切向量取线段的角平分线。** 论文只说"每个 spline 节点的切向量"，
   但没有为一个拐角曲线定义它具体是什么。它必须是 `normalize(d[i-1] + d[i])` ——
   如果用的是入射线段方向，那么该平面给出的将是对接接头（butt joint）而非斜接，
   整个要点就丢失了。
2. **退化防护。** 当转角接近180°时 `dot(T[i+1], d) → 0`，`t` 会发散。行进距离被
   截断为线段长度的8倍，并对该接头进行计数；该节点暴露了 `get_degenerate_joint_count()`，
   以便调用方知道需要细分。论文中未提及这一点。
3. **副法向量采用平行传输（parallel-transported）**而非从固定的世界坐标"上"方向
   重新推导，否则一条弯曲的脊线会发生扭转。
4. **`y` 在 `i/(n-1)` 处采样，而非论文中的 `i/n`**，因此曲线的末端会落在最后一个节点上。
   仅在两端可见差异。
5. **顶点按每个轮廓边复制。** 轮廓拐角保持硬边，扫描方向保持平滑 —— 这对于挤出体来说
   是正确的着色方式，而且不额外增加成本，因为各条带本来就是独立生成的。
6. 公式2和公式3-5是同一条代码路径：在默认值 δ = 180 时约束是失效的，结果就是纯粹
   的公式2。

验证（`SweepValidate`）：

- **锐角拐角。** 在约40°的拐角上使用圆形轮廓，`mode = Frame` 会使管状体收缩为一条
  刀锋般的边（重现图5b），而 `mode = Miter` 则让完整截面顺利通过该弯折。两种模式下
  顶点数和三角形数相同 —— 只是位置不同。
- **方向约束，数值验证。** 单位正方形轮廓，φ = 0.5，up = +Y：
  δ = 180 得到 y ∈ [-0.854, 0.854]，与45°拐角处预测值 `0.5 + 0.5/√2` 相符；
  δ = 60 得到 y ∈ [-0.5, 1.0] 且 z 不受影响，即只有顶部两个拐角移动了，且恰好沿
  副法向量移动了 φ。两条断言均 PASS。
- `MaxMiterStretch` 报告相对于线段长度的行进距离（在测试拐角上为1.16），因此它是一个
  "是否应该细分"的信号，而非一个失真度量。

（`atan2(width/2, height/2) + 6°`，上限为89°），而不是硬编码的值；论文将 δ 留给用户设定，
但对于这样一个扁平的块体来说这种做法是脆弱的。

台基 `= 2D`，立柱 `= 9D`，屋顶基座 `= 11D + bracket`，屋顶高度取自公式10，
台阶级数 `= 2^λ`。一座三开间大殿约为4.6千个三角形。

渲染过程中发现的两个 bug：

1. **ω 是由开间宽度推导出来的。** 在一座单开间亭子上，这意味着它占了整个正面宽度的75%，
   而由于 `Steps.depth = ω × 1.1`，占地面积因此变为三倍 —— 一座5米的亭子测出来宽达17米。
   表1中的 ω 是单个*栏杆构件*宽度的两倍，它应随模数缩放，而非随开间缩放：现改为
   `3.2D`，并限制在台基半宽的90%以内。
2. **屋顶望板是内外颠倒的。** 沿坡面上行意味着 z 递减，因此朴素的角点顺序会产生一个
   指向屋顶内部的法向量。在 `Cr = 1` 时不可见，因为瓦片遮住了它；只有 `Cr = 0.4` 时才
   暴露出来。值得记住：全瓦覆盖会掩盖望板方面的错误。

另请注意 `RafterCourses` 默认值为5，而非7：公式10 相对于 `n_R` 是反比关系，而论文以5
作为其最小值。取7时屋顶高度只占总高度的四分之一，看起来不像中国建筑。

### 阶段3a —— 歇山与翼角起翘 —— **已完成，已验证**

**对早期计划的一处修正：** 为了"改进硬山"而先做翼角起翘再做歇山是错误的。硬山没有翼角 ——
角部起翘需要一个带对角向角梁的歇山式转角，而硬山的两端是齐平的山墙。这里没有可供起翘的角。
因此这两个功能必须一起构建，这也正是它们在结构上相互关联的方式。

**歇山**分两层构建：

1. 一个在檐口矩形和收山内退矩形之间**放样**出来的歇山式裙檐。将内退量在 X 和 Z 方向
   取相同的距离，使得歇山脊在平面上呈45°角 —— 这正是使四个坡面共享同一坡度的关键。
   环形放样在一次操作中同时生成四个坡面*以及*四个角部的楔形体，不需要任何角部特殊处理。
2. 其上方为一段山式屋顶层，两端各带一个垂直的山花墙面。

各脊：沿脊背的正脊，沿层级边缘向下的四条垂脊，从收山转角斜向延伸至已翻起的檐角的四条戗脊，
以及一条围绕整个檐口闭合成环的滴水檐口 —— 闭合很重要，因为这正是使最后一个转角能与第一条边
斜接，而不是留下一个对接断口的原因。

**翼角起翘是一种形变，而非几何体。** 结构上，角梁更长且向上倾斜，把檐口一起带起来，因此
`CornerFlip::Apply` 是在*每一个*屋顶顶点上运行的 —— 望板、瓦片、脊和滴水檐口都会经过它，
并保持彼此一致。权重为 `(1 - d/Span)²`，其中 `d = max(距±X边的内退量, 距±Z边的内退量)`，
它只在平面转角处为零，并等于沿两条边中任一条边的沿檐距离。平方衰减使檐口在其大部分长度上
保持平坦，而在接近转角处急剧起翘。起翘在 Y 方向抬升，出翘在 X 和 Z 方向对角向外推出。

已验证：关闭翻转时 X 方向范围为13.1，默认值下为14.3，3倍强度下为15.5 —— 且**顶点数和
三角形数完全相同**，证实这是一种纯粹的形变。全部表1断言依旧通过。一座歇山大殿约为11千个
三角形。

渲染过程中发现的一个 bug：**瓦片层与望板共面，产生 z-fighting，形成一片斑驳的混乱。**
无论翻转开启还是关闭都会出现，因此不是翻转导致的问题。`MakeTileContour` 增加了一个
`Lift`，将弦抬高出表面 `0.07D` —— 这在物理上也是正确的，因为瓦片本来就搭在望条上。
值得作为该模块的一条通用规则记住：任何铺设在生成表面上的扫描体都需要一个明确的抬升量。
（阶段6完全替换了这些管状体，并将该常量移入了 `TileSection::MinimumLift()`，
由瓦垄槛深推导得出，因此它再也不会与其要避开的瓦片脱节。）

### 阶段3b —— 庑殿 —— **已完成，已验证**

庑殿和歇山是同一个函数 `BuildHippedRoof(Spec, bFullHip, Mesh)`。庑殿是同一个歇山式外壳，
只是把内退量一直取到进深的一半：内侧矩形收缩为一条线，而这条线**就是**正脊。歇山中被称为
戗脊的对角脊，在庑殿中变成垂脊，无需任何改动。因此整个屋顶类型只花了大约十五行的开关代码。

一个令人愉快的结果：一个**正方形**平面在全庑殿下会使脊线收缩为一个点，这正是一个攒尖锥体 ——
经渲染验证正确，因此集中式家族的一部分已经可以通过这条路径抵达。当正脊长度为零时，
它会被跳过。

在此期间瓦片层也得到了改进：现在它们是按**檐口**范围来分布间距的，并且每一层都会在跑出
面之外时被**裁剪**。这使歇山的转角楔形体和庑殿的三角形山尖两端都得到了铺瓦，此前这两处
都露出裸望板。它在山尖处留下了一条锯齿状边缘，而不是真实翼角所具有的裁瓦扇形 ——
近距离可见，但在远处看起来像纹理。

### 阶段4 —— 插件与 PCG 集成 —— **已完成，已验证**

`Game/addons/ancient_building/` —— `plugin.cfg`、`plugin.gd`，以及一个 Flow 节点。

- `plugin.gd` 通过 `FlowNodeRegistry.register_node_directory()` 注册节点目录。
  **这是该 API 的第一个使用者** —— 它此前已存在于插件中，但没有任何代码调用过它，

### 阶段5 —— 全部九种屋顶类型，加上斗拱与门窗 —— **已完成，已验证**

**三套生成器覆盖九种类型**，正如公式8所预测的：

| 生成器 | 类型 | 差异所在 |
|---|---|---|
| `BuildGabledRoof(bOverhang, bRolled)` | 硬山, 悬山, 卷棚 | 山墙悬出；卷曲脊 |
| `BuildHippedRoof(EHipTop)` | 庑殿, 歇山, 盝顶 | 外壳终止方式：脊线 / 山式屋顶层 / 平顶 |
| `BuildCentralisedRoof(ECentralProfile)` | 攒尖, 圆攒尖, 盔顶 | 轮廓形状与面数 |

关于每一种值得了解的地方：

- **卷棚**是由*一条连续未中断的轮廓*从一侧檐口越过屋脊卷曲部分延伸到另一侧檐口构建的，
  而不是两个坡面加一个盖顶。因此一条瓦片层用一次扫描就能贯穿整个屋顶，这正是真实卷棚
  的做法。
- **盝顶**只是歇山式外壳的第三种终止方式：提前停止，用一个平面多边形封顶，再用一圈
  围脊环绕。
- **集中式家族需要一个多边形平面**（公式8），因此它位于自己独立的文件
  `PolygonalBuilding.cpp` 中，拥有自己的台基/立柱/墙体/栏杆。`PlanPolygon` 将顶点
  放置在 `2πk/N + π/N` 处，以使边朝向坐标轴 —— 否则 N=4 会得到一个菱形而不是正方形。
- **圆攒尖**是攒尖被强制为至少24个面、并关闭了转角翻转和脊线的版本。圆锥体是去掉了
  转角的金字塔，而不是一种独立的构造。
- **盔顶**是一个鼓起的轮廓：`(1-T) + bulge·sin(πT)·(1-T)` 将下部坡面向*外*推离直线，
  从而给出盔顶那种膨起的肩部。论文特别指出这是它所替代的方法无法实现的情形。

多边形渲染过程中发现的两个 bug：

1. **转角翻转的跨度是从进深推导出的**，在一个八边形面上会覆盖整个面，使屋顶变成了
   一个有褶皱的雨伞。多边形平面现在改为将该跨度按面弦长缩放。
2. **收敛于一个顶点的脊线相互重叠，形成了一个尖刺状的顶冠。** 它们现在在90%高度处
   停止，宝顶盖住了这个交汇点 —— 这正是宝顶实际的用途所在。

此外还实现了：**翼角切瓦**（裁剪后的瓦片层现在精确落在戗脊线上，消除了锯齿状边缘）、
**斗拱**（座斗块承托多层交叉的拱、带升块 —— 仅用盒体实现，但逐级出挑的轮廓已能读出来）、
以及**门窗**（在正对开间处设有双扇门框的板门，其余开间为槛墙加棂条格窗；格窗用条状网格
实现，因为贴图会破坏无素材的约定）。

调优笔记：第一次尝试的格窗使用了0.33米网格、两组交叉的窗条，整个上部墙面看起来像红色
木构而不是带窗的粉墙。改为更疏的间距、更细的窗条和更高的槛墙后修正了这个问题。
补间铺作的中间斗拱组也被去掉了 —— 在这个尺度下它们使整条斗拱带挤成了一整片。

成本：硬山大殿约9.6千个三角形，歇山约18千，庑殿约17千，八角攒尖约18.5千。

### 阶段6 —— 编辑器面板 —— **已完成**

`AncientBuildingEditorPlugin`（`Source/AncientBuilding/`），在 C++ 层通过
`EditorPlugins::add_by_type` 在 `MODULE_INITIALIZATION_LEVEL_EDITOR` 处注册 ——
与树面板做法相同，因此没有 `plugin.cfg`，`addons/` 下也没有需要启用的内容。

**它是上下文相关的**：`_handles` / `_edit` / `_make_visible` 只在选中一个
`AncientBuilding` 时才显示它。该面板只被一次性挂载到 `CONTAINER_SPATIAL_EDITOR_SIDE_RIGHT`，
之后只是被显示或隐藏。

这个挂载位置是刻意选择的。第一次尝试使用了 dock 插槽，但这在此处是错误的做法：
根据选中状态动态添加/移除一个 dock，会在用户最需要 Inspector 的那一刻恰好抢走
Inspector 的标签页（`DOCK_SLOT_RIGHT_BL` 与它共享同一个插槽），而且 dock 插槽本身是
一个 `TabContainer`，它自己掌管子节点的可见性，因此简单的 `set_visible()` 在那里
根本无法使用。而一个空间编辑器侧边容器则没有这两个问题。

由于该面板是上下文相关的，它**不**创建节点 —— "添加到场景"按钮本来就无法触达，
而且这样做本来也是多余的，因为 `AncientBuilding` 是一个已注册的类，Godot 的
"添加节点"对话框本身就已经提供了它。去掉这个按钮同时也去掉了一个重复的屋顶选择器；
现在只有一个在起作用。

Inspector 已经暴露了全部约50个参数，因此该面板刻意不去镜像它们。它承载的内容是：

- 一个**按生成器分组（脊式、歇山式、集中式）、列出全部九种类型的屋顶选择器**，
  英文和中文标签均有，外加带 UndoRedo 支持的"添加到场景"。
- 一个**表1推导结果的实时读数** —— 模数 D、檐口高度11D、台基2D、总高度。这才是该
  面板真正的意义所在 —— 整套设计的核心就是"一个数字推导出其余一切"，设计者拖动
  Width 时应该能看到这一点发生。
- 值得来回调整并对照视口观察的旋钮：宽度、进深、开间数、边数、椽子道数、屋顶高度、
  转角起翘量、瓦片覆盖率，以及栅栏/台阶/墙体的开关。

**它强制执行公式8的耦合关系**，这是 dock 唯一能够防止出现令人困惑结果的地方：
选择集中式屋顶会将四边平面吸附为八边形，并将进深锁定为等于宽度，同时禁用进深和
开间数输入，因为多边形平面必须是规则形。切回脊式屋顶会恢复为四边。

注意 `sides = 4` 配合集中式屋顶是*合法*的，不是错误 —— 它给出一个以矩形基座和主体、
上覆收敛屋顶的方形平面攒尖。吸附到8是一个更好看的亭子默认值，因此它只在进入时
应用一次，而不是强制执行。

已验证：编译干净，编辑器加载时零错误零警告，`Game/Develop/BuildingMatrixValidate.tscn`
遍历全部九种屋顶类型，应用该面板自身的平面合法性规则，断言每一种都生成了具有有限
边界、位于地面以上的真实几何体，且表1依旧成立 —— **9/9 全部通过**。这覆盖了 dock 的
契约部分；面板控件的布局本身尚未经过人工检查，因为无头（headless）编辑器无法显示
dock。

### 阶段6 —— 瓦面 —— **已完成，已验证**

瓦面部分被重新构建，因为它在种类上就是错的，不只是细节问题。在阶段5之前，每一垄瓦
是一根单独的半圆管状体，铺设在一个平坦的望板表面之上，因此屋顶在各脊之间存在一段
*平坦区间* —— 而这是任何中国屋顶都不会有的。近距离渲染时它看起来像波纹钢板，而且
它消耗了**整座建筑三角形总数的大约三分之二**，因为每根管状体都携带了一个封闭的周边，
包括没人能看到的底面。

真实的屋顶是一整片连续的鳞状表面：板瓦形成凹槽，筒瓦覆盖在接缝处。因此
`Source/AncientBuilding/TileSkin.*` 将其作为一个位移表面来生成，而不是一堆管状体。
调用方掌控屋顶的参数化方式 —— 各垄瓦在何处、以及某个歇山转角在何处将其截断 —— 并
按截面采样交出一列点；瓦面模块自己掌管横截面、明暗和檐口瓦片。

`TileSection` 是每垄瓦在一个坡度单位内的八个采样点：

| 采样点 | 偏移 | 高度 | 作用 |
|---|---|---|---|
| 0 | −0.500 | −0.17 | 板瓦槛底部，与前一垄共享 |
| 1 | −0.155 | 0 | 板瓦边缘 —— 折痕 A |
| 2 | −0.155 | 0 | 筒瓦底部 —— 折痕 A |
| 3–5 | −0.110 … +0.110 | 最高 +0.16 | 筒瓦两侧、顶部、两侧 |
| 6 | +0.155 | 0 | 筒瓦底部 —— 折痕 B |
| 7 | +0.155 | 0 | 板瓦边缘 —— 折痕 B |

该表中有三点是关键所在：

- **筒瓦比其所在的槛更窄**，大致为1:2。等宽会产生一条正弦波；肉眼需要一根圆形的
  棱线搭配一条宽阔的槛才能读出"瓦"而非"波纹"。这是最大的单一视觉杠杆，
  超过槛深本身的影响。
- **两对折痕在位置上重合，仅法向量不同。** 它们的四边形是退化的，因而被丢弃，
  因此硬边的筒瓦轮廓*不消耗任何三角形* —— 它完全是靠 `MeshAccumulator::AddQuadSmooth`
  实现的，该函数为每个角点接受一个法向量。
- **板瓦的几何体是一条直线坡道，但它的法向量是一条抛物线。** 正确采样这条曲线要
  消耗瓦面整体成本的25%，而这仅在檐口轮廓处可见，滴水本来就会遮住那里。平滑法向量
  完全能够在平坦几何体上表现出一条弯曲的槛。

望条抬升量现在来自 `TileSection::MinimumLift()` —— 槛深加上一个净空，而不是在每个
调用处手工选定的 `0.07D`。那个常量正是导致阶段3a出现 z-fighting 的原因；将其绑定到
截面自身的深度，意味着它不会再与瓦片脱节。

**瓦当和滴水**由瓦面模块生成，而不是由调用方生成，因为只有它知道位移之后筒瓦和
板瓦槛落在何处、处于什么坐标系中。它们是屋顶上单位三角形性价比最高的细节 ——
`O(courses)`，而不是 `O(courses × rafters)` —— 却位于玩家在地面上能看到的唯一
屋顶边缘上，并且正是它们把截面产生的原始锯齿变成了中国屋顶赖以辨认的镶边滴水线。
滴水的脊线需要**三个**节点：瓦片沿屋面延伸而后其外缘向下折转。用两个节点时它除了
从正外侧看以外都不可见，且会被读成瓦当之间的一个缺口。

`ETileEaves` 指明一列瓦垄的哪些端点是檐口。瓦垄的走向是从檐口开始的，因此通常是
`AtStart`；卷棚是 `AtBothEnds`，因为它的单一轮廓从一侧檐口越过卷曲部分延伸到另一
侧檐口；歇山上层是 `None`，因为它的下缘是收山断口下方的博脊，而不是檐口。当
`tile_coverage` 小于1时，屋顶是从檐口向上开始裸露的，因此第0垄位于坡面中途，
也会被设为 `None`。

添加檐口瓦片还引发了另一处改动：原来那条连续的滴水扫描体挡在它们**前方**，把它们
全部遮住了。现在它变成了一条细窄的连檐板，被下压并后退，从而读作瓦垄止于其上的
木构件。同一个元素，尺寸更真实。

两项值得明确记录的成本：

- 瓦面与管状体相比，同一场景同一参数（歇山，11×7米）：每垄瓦的边际成本从**362
  三角形增至391三角形**，约+8%。我原以为它会*更便宜*，这个预测是错的 —— 瓦面
  拥有8个截面面片，而管状体只有6个，其中两个是它看不见的底面。第一次尝试的成本
  是+40%，直到把板瓦中间采样点做出来之后才降下来。
- 檐口瓦片在一座歇山大殿上增加了**+42%**的成本（18,960 → 26,864）。这是刻意的：
  它是整个屋顶中每三角形性价比最高的细节。

在集中式家族上，各垄瓦向顶点收敛，因此其间距会随平面半径收缩，一路收到底时筒瓦
会变得比一个像素还窄。`TILE_APEX_CUTOFF` 使瓦面在檐口边心距的0.22处停止，
`BuildFinialBase` 把宝顶的砌体鼓座覆盖在接合处上方 —— 这正是真实攒尖的做法。

一条方法论上的笔记。收敛的顶冠*看起来*是破损的，直到预览场景打开了 MSAA：
本以为是几何体损坏，实际上纯粹是采样噪声。**要在开启抗锯齿的情况下判断生成的
几何体**，否则锯齿问题和形状问题是无法区分的。

### 阶段7 —— 屋顶望板 —— **已完成，已验证**

从下方看屋顶是透空的：站在檐口下能看到椽子之间的天空，掠射角度下甚至能直接
穿透近侧坡面看到远侧坡面的背面。

显而易见的猜测是法线方向反了，而这个猜测是错的 —— 值得记录下来，因为这两种
失效模式从平常查看的那个角度看起来完全一样。`RoofSoffitDiagnose.tscn` 按法向量
Y 分量的符号对屋顶的每个三角形分桶：

```
修复前：  up=14698  down=4571  side=4763     最低的向下面在 y=9.25 处（檐口线）
```

一个翻转的法向量也会使表面从**上方**看不见，而事实并非如此。而那4571个向下的面
全部属于封闭实体 —— 斗拱、脊的扫描体、封顶的瓦当和滴水 —— 没有一个属于屋面本身。
望板在全部五处生成位置上都只是一个**零厚度的单面表面**。没有可以剔除的东西；
那里根本什么都没有。

修复方法是给望板增加厚度，而不是关闭背面剔除。剔除是免费的，但它会翻转每个
底面的光照，暴露每个实体的内部，并与计划中的 NPR 着色相冲突。`AddRoofPanel`
生成迎风面、其下的望板底面，以及 —— 通过 `ERoofPanelEdges` 标志 —— 在开放边缘
处将二者闭合起来的收边。这个收边同时也阻止了檐口读成一条刀锋般的边。卷棚正是
该标志需要是一个集合而非一个布尔值的原因：它的轮廓从一侧檐口越过卷曲部分延伸到
另一侧檐口，因此它最后一块面板的*上*边缘也是一个檐口。

**望板必须垂直向下偏移，而不是沿各面板自身的法向量偏移。** 沿每个面板自身法向量
偏移，会在每一处坡度变化的接缝处把表面撕开 —— 相邻面板会把它们共享的角点推向
不同的方向 —— 第一次渲染出来时整个底面布满了细密的裂纹。垂直下压使每个面板获得
相同的位移，因此共享的角点保持共享，望板底面保持不透水。这也与举架相符，
举架的深度本来就是按垂直方向计量的。这样测得的厚度在垂直于坡面方向上会随坡度
变化，而这对于搭在椽子上的一层甲板来说本来就是正确的。

成本几乎可以忽略：**硬山上+24个三角形，盔顶上+1680个**，占比0.2%–7%。望板
从来都不是昂贵的部分 —— 瓦面才是。


- **多重檐**（图3展示了上/中/下层屋顶）。这是论文中唯一仍未实现的项目，
  它不只是又一种屋顶类型 —— 它需要把*主体*变成多层结构：每一层都有一条墙带
  和斗拱带，并在逐层收缩的平面上于每一层生成一个屋顶。这是对 `BuildBody` 的
  改动，因此暂不实施，而不是草率赶工。
- **檐口下没有椽子（椽）。** 望板目前只是一层朴素的望板甲板；真实的悬挑会露出
  椽子和飞椽穿过它，而这是整座建筑在地面视角下被看得最多的表面。添加成本低 ——
  沿檐口每根椽子加一个小盒体即可 —— 但屋顶要读得实在并不必须它。
- **没有沿坡向的层次感。** 沿坡面重叠的瓦片*行*被估算约为瓦面本身成本的2.5倍，
  因此推迟实现；有了瓦当和滴水之后，屋顶已经能读作瓦面，因此这现在是一个
  近景 LOD 的问题，而不是一处缺口。
- 多边形路径上的门窗；那些墙体目前仍是朴素的墙板。
- 内部梁架，目前没有任何东西能看到它。
